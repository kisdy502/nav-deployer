# 需求管理规范

> 本工作区的需求统一在 `requirements/` 下用 Markdown 管理，**不使用 GitLab / Jira 等外部 Issue 系统**。
> 本文件是需求管理的完整规范（三级流转流程 + 需求文档写法 + agent 行为约定）。
> 位于 `.claude/rules/`，由 Claude Code 在每次会话启动时自动加载，无需手动查阅或引用。

---

## 一、三级流程

```text
原始需求文档（requirements/specs/主题.md）
        ↓
单个用户故事（requirements/stories/故事.md）
        ↓
开发任务（requirements/tasks/任务.md）
```

业务需求必须按此顺序管理。一个层级只承担自己的职责，不用下游对象替代上游对象。

### 第一层：原始需求文档

**载体与粒度**

- 原始需求存放于 `requirements/specs/`，**文件名即标题、不加编号**，例如 `质检报告规格.md`。
- 一篇文档只记录一个业务主题，可以包含多个后续用户故事。
- 原始需求是长期设计记忆，不标状态，也不用它追踪具体开发进度。

**文档内容**

原始需求应记录已确认且跨多个故事稳定成立的内容：

- 背景与动机、产品目标、用户价值；
- 领域概念及其业务定义；
- 已确认的业务规则、边界、范围外内容；
- 竞品或交互参考的采纳与拒绝结论；
- 候选用户故事地图及其依赖关系；
- 对应故事的相对路径链接。

原始需求只描述 what/why。数据表、接口、类名、文件路径和具体实现方案由开发阶段基于代码库确定，不写入原始需求。

### 第二层：单个用户故事

**载体与粒度**

- 每个可独立交付的用户故事在 `requirements/stories/` 下建一个 Markdown 文件。
- 一个文件只承载一个用户可感知的完整行为；不能将多个故事、完整规格或技术方案合集写进同一个文件。
- 文件名即标题，使用不超过 30 字的中文动宾短语；文件内以相对路径回链原始需求文档。
- 文件头部写一行状态字段 `状态: 规划中`。
- 故事内容（背景、角色与意图、功能描述、规则、验收标准、范围外、依赖）严格遵循下文「二、需求文档写法」。

**创建顺序**

1. 先完成或更新原始需求文档，明确本次主题的稳定决策。
2. 提出候选用户故事的标题、交付结果与阻塞关系，请老大确认拆分粒度。
3. 获确认后，按依赖顺序在 `requirements/stories/` 建文件，状态置为 `规划中`。
4. 将故事文件名与相对路径回填到原始需求的故事地图。

未确认的候选故事不建文件。已经建立的文件如发现粒度不对，应收敛为一个故事或拆分为多个故事，不能继续扩写为聚合规格。

### 第三层：开发任务

**载体与粒度**

- 在用户故事确认可实施后，在 `requirements/tasks/` 下建任务文件，头部以 `所属故事: ../stories/<故事>.md` 回链所属故事。
- 一个任务描述该故事内一项可验证的实现工作，包含"要交付什么""完成条件""阻塞于什么"。
- 文件头部写一行状态字段 `状态: 规划中`。
- 任务可按实现顺序拆分，但不把无独立验证价值的文件级操作单独作为任务；优先形成可编译、可演示或可验证的纵向切片。
- 任务的范围不得跨越所属故事；新增业务行为时先创建或调整故事文件，而不是在任务里悄悄扩展需求。

**创建顺序**

1. 读取所属故事的规则、验收标准和依赖。
2. 提出任务标题、交付结果和阻塞关系，请老大确认粒度。
3. 获确认后建为 `requirements/tasks/` 下的文件，并在头部回链所属故事。
4. 每个任务完成后更新自身状态；所属故事的全部验收标准通过后，才将故事状态更新为 `测试中`。

### 状态与追溯

- 用户故事使用 `状态: 规划中 → 开发中 → 测试中` 表达阶段；验收通过后改为 `状态: 已验收`。
- 开发任务的状态反映具体执行进度，不替代所属故事的验收状态。
- 原始需求文档、用户故事、开发任务与提交信息必须可以相互追溯：故事回链规格，任务回链故事，commit 描述与故事标题保持一致。
- 新业务需求先建立原始需求与用户故事；小型 bug 修复或纯代码优化可直接处理，无需强制建立原始需求。

### 执行检查

开始开发前确认：

- 原始需求文档已存在且包含当前故事的稳定业务规则；
- 当前故事文件只描述一个用户故事，且验收标准二元可判；
- 当前开发任务属于该故事，范围、完成条件与阻塞关系明确；
- 没有将原始规格全文复制进一个故事文件，也没有跳过用户故事直接从原始需求开发。

## 二、需求文档写法

### 定位

- **形态**：用户故事（User Story），细粒度——一个故事 = 一个可独立交付的功能点，满足 INVEST 原则（Independent / Negotiable / Valuable / Estimable / Small / Testable）
- **读者**：人和 AI 双读者。单文档内分层：背景/角色/描述（给人看价值与动机），规则/验收（给 AI 执行）
- **职责边界**：需求文档只写 what/why。数据模型、接口定义、技术方案不属于需求文档，由开发阶段从代码库探索确定
- **适用范围**：业务功能需求使用本模板；纯技术/重构工作（如"重构模块 X"）不硬套用户故事格式，可用简短文描述

### 故事模板

可直接复制的模板见 `../../requirements/README.md`。字段结构如下：

| 字段 | 必填 | 说明 |
|------|------|------|
| 背景与动机 | 强制 | 现状问题与动机。写具体问题，禁止"提升用户体验"类空话；有可量化代价/收益就写，没有不写（状态流转类需求可一句话带过） |
| 角色与意图 | 强制 | As a / I want / So that。角色写业务实称（如"质检员"），项目内统一叫法；无明确用户角色的需求（系统行为类）可省略角色行，保留"想要"行；So that 有真实价值才写 |
| 功能描述 | 强制 | 主流程叙述，一句话也行（"任务详情页 → 导出焊缝清单 → 下载 Excel"）；复杂流程写完整主流程 |
| 业务规则 | 强制 | 编号化 R1/R2…，边界与异常场景必须显式列出 |
| 验收标准 | 强制 | 编号化 AC1/AC2…，二元可判（通过/失败） |
| 范围外 | 可选 | 本期明确不做的内容，防止实现跑偏 |
| 依赖 | 可选 | 依赖的其他故事/系统 |
| 非功能指标 | 可选 | 量化指标（如"10 万行导出耗时 < 10s"），禁止形容词（"快速""流畅"） |

### 编写纪律

1. **编号即语言**：故事内的业务规则与验收标准必须编号（R1/R2…、AC1/AC2…），验收引用规则编号（"文件名符合 R2"）。评审、提问、AI 实现均使用编号沟通。
2. **规则与验收绑定**：每条业务规则至少被一条验收标准覆盖；规则与验收脱节 = 需求没写完。
3. **验收二元可判**：通过/失败明确，禁止"更快""更好""合理"等模糊词。
4. **一条验收一个行为**：G/W/T 的 When 只能一个动作，准备步骤放 Given，多个结果拆多个场景。
5. **数量控制**：每故事 3-5 条验收标准，超过 6 条说明故事太大，应拆分。
6. **边界显式编目**：与本故事相关的边界场景（空数据、越权、并发、重复操作等）必须显式写出，不相关的不写。禁止"优雅处理错误"式写法。
7. **背景防套话**：写具体现状问题；有可量化代价/收益就写，没有不写。
8. **角色实称**：角色写业务实称并保持项目内统一叫法。

### 引用

- 跨文件引用写相对路径（如 `../specs/质检报告规格.md`）。
- 在回复、代码说明中引用需求时写文件路径（如 `requirements/stories/焊缝清单导出.md`）。
- commit 描述与需求标题保持一致（需求「焊缝清单导出」→ `feat: 新增焊缝清单导出`），便于双向反查。AI 提交时遵守，人工提交可放松。

## 三、agent 行为约定

- 讨论新功能／新页面／新交互并准备实现时，**先在 `requirements/stories/` 落一个故事文件**，并在回复中给出文件路径。
- 老大明确要求"暂不建需求"时，只输出方案，不建文件。
- 小 bug 修复或纯代码优化可不建需求。
- 实现相关代码时，在说明里引用对应需求文件路径。
- 开发完成后把对应故事的状态改为 `测试中`，并在回复中说明改了哪个文件；`已验收` 由老大决定，不擅自推进。
- 状态由老大驱动，agent 只推进到「测试中」为止。

## 四、目录说明

```text
requirements/
├─ README.md      # 目录说明与可复制的文件模板
├─ specs/         # 第一层：原始需求文档（长期设计记忆）
├─ stories/       # 第二层：用户故事（可独立交付的功能点）
└─ tasks/         # 第三层：开发任务（可验证的实现工作）
```
